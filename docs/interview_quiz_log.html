infra/budget.tf

2026-08-02

What it is

infra/budget.tf sets up a real dollar spending cap for this project's Azure account. It's part of the Terraform setup that builds all the cloud infrastructure, and it works by watching actual spending and emailing an alert as it gets close to the limit — currently $10/month.

How it's implemented

It creates one Azure Budget attached to the whole resource group, so it tracks total spend across everything in the project — database, backend hosting, storage, all of it. It sends three separate warning emails: one once you've actually spent 50% of the budget, another at 80% actually spent, and a third if Azure predicts you're on track to hit 100%, even before you actually get there. The dollar amount and the alert email are both set through variables rather than hardcoded, and a small rule tells Terraform to ignore a date field Azure updates on its own every month, so that doesn't look like an unwanted change.

Concept(s) it demonstrates

Infrastructure as Code — describing cloud setup in a version-controlled text file instead of clicking through a web console. And a cost guardrail — an automatic safety check that catches an expensive mistake (like an accidentally oversized resource) before it turns into a surprise bill.

Why this approach, and what else was considered

A real spend-cap alert was added on top of picking small, free-tier-sized resources, because careful sizing alone can't catch every mistake — the project's own docs call this "the real backstop, not just careful sizing." Relying only on free-tier resource choices is simpler to set up, but gives no warning if something ever gets misconfigured to cost more than expected.

What could be better next time

The alerts are informational only — they send a warning email but can't automatically pause or shut anything down, so a person still has to notice and react before costs keep climbing.

Likely interview questions

  1. "Why three separate alert thresholds instead of one?" — early warnings at 50%/80% actual spend give time to react, while the 100% alert fires off a forecast, catching a problem before it actually happens.
  2. "What does the lifecycle rule do here?" — it tells Terraform to ignore Azure's automatic monthly date rollover on the budget period, so that doesn't get flagged as a change to undo.
  3. "Why attach the budget to the whole resource group instead of one resource?" — a cost overrun could come from any resource, so watching the group as a whole catches surprises the author didn't specifically plan for.

etl/load.py

2026-08-02

What it is

etl/load.py takes the FIFA World Cup data — already cleaned up by transform.py — and saves it into the project's Postgres database. It's one script in a 3-step pipeline: clean the data, define the tables, load the data in. You run it by hand or with make etl-run; the main app never runs it itself, it just reads what this script already saved.

How it's implemented

It reads the raw CSV, cleans it up using transform.py, then connects to the database using a connection string from an environment variable (and stops immediately with a clear error if that's missing). First it sets up the database tables. Then it empties the old data and inserts the new data, table by table, in an order that respects which tables depend on which — using batched inserts (many rows at once) rather than one row at a time, which is much faster. Last, it refreshes a few summary views the rest of the app reads from. If anything fails partway through, the changes are undone instead of leaving things half-saved.

Concept(s) it demonstrates

Idempotent writes — running it twice gives the same result, not duplicates, because it wipes and reloads rather than appending. Respecting foreign keys — tables are loaded in an order that makes sure nothing points to data that isn't there yet. Batched inserts — saving many rows per trip to the database instead of one at a time, which is much faster.

Why this approach, and what else was considered

Wiping and reloading the tables each run is simple, and works well here because the source is one complete file, not a stream of new records to merge in. A tool like Airflow or dbt handles more complex, multi-source pipelines better, but would be overkill for a single CSV loaded occasionally by hand.

What could be better next time

Wiping the tables also accidentally wipes a couple of related tables (like saved AI-generated embeddings) every single time it runs — that's documented, but only fixed with a printed reminder to regenerate them, not a real fix. A cleaner version would avoid touching those tables at all.

Likely interview questions

  1. "What happens if this fails halfway through a run?" — the database changes happen inside a transaction, so a failure undoes the partial work instead of leaving things half-saved.
  2. "Tell me about a real bug this had." — a comment right before one table's setup code accidentally made the script skip creating that table entirely, while still reporting success; it was found, fixed, and now has a test that checks for it.
  3. "Why does rerunning this wipe out unrelated data?" — deleting a table's rows cascades to anything that references it, which reached further than intended; worth discussing safer, more targeted alternatives.
